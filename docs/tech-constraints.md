# Tech constraints

Listing fields, transaction processes, integrations and other technical
constraints the planning project needs to know about. Do not put secrets in
this folder; it is synced to Claude.ai.

*Last checked against the repo: 2026-10-20. Claude Code keeps this current.*

## Stack
- **Platform backend:** Sharetribe. On the **Pro** plan, which lets us build with Extend features in Dev but not publish custom code live until we upgrade to **Extend** ($299/mo).
- **Platform frontend:** customized Sharetribe Web Template (React/Node), self-hosted. Repo `regan-revie/revie-dev`. Dev deploy on Render (`revie-dev.onrender.com`): web service on the Starter plan plus Postgres (`revie-dev-db`), both in Frankfurt.
- **Marketing site:** Webflow. Not being rebuilt; out of scope. The platform should still feel like the same brand when someone clicks through from it.
- **Go-live:** January 1, 2027 (includes the upgrade to Extend).
- **Implementation:** Regan with Claude Code.

## Environments
Three Sharetribe environments, each with its own hosted configuration (listing types, branding, logo, Stripe), so they drift silently:
- **Dev** (flex-cli marketplace id **`revie1-dev`**; `revie_dev` is only the marketplace's display name, and flex-cli rejects it): the only one that supports custom code; what this repo develops against. Private marketplace. Use `npx flex-cli ... --marketplace revie1-dev` (flex-cli is not installed globally; Regan is logged in, and the key must never be read or printed).
- **Test:** a no-code preview meant to mirror Live. Console config changes are made here and copied to Dev and Live.
- **Live:** production. A public marketplace, currently running Sharetribe's hosted frontend, not this codebase.

## What's already built (platform)
- **Nylas calendar integration:** coaches connect Google/Outlook; availability comes from their real calendar. Booking, payment capture and confirmation work end to end (first real booking 2026-09-13).
- **Working hours:** the availability endpoint reads `publicData.nylasOpenHours` per listing (one window of days + start + end) and filters slots by it. **Nothing in the repo writes that field**, so coaches have no way to set working hours; it has to be set by hand. A coach with no hours set is simply bookable at any time the calendar is free.
- **No coach-facing UI for the Nylas flow exists.** The server endpoints are there (`/api/nylas/connect`, `/callback`, `/enable-listing`), but nothing in `src/` calls them: a coach cannot connect a calendar, choose one, or switch a session to calendar booking from the product. Only the client-side booking, checkout and cancel/reschedule UI is built.
- Render service with Postgres, verified webhook path with HMAC signature checks
- Custom booking UI replacing Sharetribe's, plus client cancel/reschedule (built; not yet exercised live end to end)
- **Booking creation after payment is now server-owned and recovers from failure** (branch `payment-failure-recovery`, not yet deployed). `server/api/nylas/bookingRecovery.js` `ensureBooking()` takes a Postgres claim (`nylas_booking_attempts`), makes up to two attempts (a network error, 408, 429 or 5xx is retried; "slot taken" or a rejected key is not), waits about 10 seconds for a late `booking.created` webhook, then runs `transition/operator-decline` (full refund, cancels the uncaptured card authorisation per Sharetribe's documentation) and logs to Sentry with the code `nylas-booking-failed-declined`. A webhook arriving after a decline cancels the orphaned Nylas booking (`nylas-orphan-booking-cancelled`). A 60-second sweeper in the web service (`server/jobs/`) handles paid bookings older than 3 minutes that the browser never reported. Sentry only records anything if `REACT_APP_SENTRY_DSN` is set in Render, and an alert rule is still needed for the email to Regan. Unproven end to end: the SQL has not been run against a real Postgres, and the Stripe test-mode check and the Dev process rollout are still to do.
- Google SSO, Integration API wired up
- **Brand tokens in `src/styles/revieTokens.css`**, imported after `marketplaceDefaults.css`. Lives on branch `revie-design-tokens` and is not yet committed or merged to `main`.

**Listing setup**
- Listing type `signature-session`, process `default-booking/release-1`, `unitType: fixed`, `availabilityType: oneSeat`, 20% provider commission
- Listing fields, the same in Dev, Test and Live: `identity`, `communication_style`, `structure`, `language`, `coachlocation`, `pre_work`
- One difference: Dev and Test have a `length` field; Live has `timezone` instead (a workaround for Sharetribe having no per-coach timezone; don't build anything on it)

Decision (Oct 26): drop it and don't add it to Live; session length comes from price variations (below). No code, translation, config or doc in the repo reads it. Live has `timezone` instead and no `length`.
- Listing types and fields are hosted config in Console. The repo's local config files are the stock template, commented out, so the repo alone doesn't show them.

**Not built yet**

## Emails
Every email today is a Sharetribe built-in. The default-booking process (`ext/transaction-processes/default-booking/`) sends:
- **At payment (`confirm-payment`):** release-1 emails the coach "You have a new booking request", the stock accept-or-decline wording. Process release-2 (in `ext/`, not yet pushed anywhere) removes it, so a coach is not emailed before the booking exists.
- **At `operator-accept`:** the client gets "Your booking request was accepted"; the coach gets an operator-accepted email.
- **At expiry / decline:** the client gets "request expired" or a failure email. In release-2 the failure email (sent by `operator-decline`) says the booking didn't go through and nothing was charged, and the expired email has a body for fixed-length sessions. The provider's "declined on your behalf" email is removed.
- **After the session (`complete`):** payout ("money paid") email to the coach and review requests to both.
- **Cancellation:** from release-3, `transition/cancel` emails the client (full refund on its way, amount from `payin-total`) and the coach (session cancelled). Release-2 sent nothing. The client email states the refund unconditionally, which is safe because `cancel` always runs `calculate-full-refund` + `stripe-refund-payment`; from release-4 a client cancellation inside 48 hours runs `transition/late-cancel` and has its own emails (see below). The cancel emails deliberately carry **no session date**: Sharetribe's booking record never changes after a reschedule, so a date there could be the original time.
- **Not covered at all:** reschedules, payment expiry and any reminder before the session.
- **Session listings are made bookable automatically, by the server (`ensureBookable.js`).** A coach with a connected calendar needs no manual step: every minute `reconcile.js` (started from `server/jobs/`, needs `DATABASE_URL` and the Integration API credentials) lists published listings with their authors and, for each coach who has a grant, makes sure each session listing has what a booking needs, all written in one update: a Nylas configuration per session length (price variant), the calendar, `nylasOpenHours`, the notice period, `calendarBookingEnabled`, the process alias (`BOOKING_PROCESS_ALIAS`, because a new listing is stamped with the listing type's release-1) and an availability plan whose timezone is the hours' zone. The same routine runs from the Nylas callback (after a connect) and from `POST /api/nylas/sync-me` (the logged-in coach's own listings, for the Calendar page after saving hours); `enable-listing` is now a wrapper that forces it with a chosen calendar. A per-coach Postgres advisory lock (`withAdvisoryLock`) stops two of them syncing the same coach at once.
  - **Idempotent by signature.** Everything the result depends on (grant, lengths, title, coach name, hours, notice, alias, the coach's own timezone choice, a code version) is hashed into `publicData.nylasSyncSignature`. A listing that already carries the current hash costs nothing: no Nylas call, no Sharetribe write. Bump `SYNC_VERSION` to re-sync everything once.
  - **Listings enabled before signatures existed are adopted, not rewritten**: if their stored configurations, calendar, hours and timezone are already what a sync would write, only the signature is stamped. An already-enabled listing also keeps the process alias it is on. Dry-run against the Dev Test Session listing: adopted, one key written.
  - **Where hours come from:** the coach's `privateData.bookingHours` (`{timeZone, days (1 = Mon ... 7 = Sun), start, end}`, saved from the Calendar page); else the hours the listing already has; else **Mon-Fri 09:00-17:00**. The availability endpoint also applies Mon-Fri 9-17 to any listing whose hours are missing or unusable, so nobody is ever bookable 24/7. Hours are applied when slots are offered, not checked when a booking is created (no initiate-time check, by decision).
  - **Both a connected calendar and payout details (`stripeConnected`) are required for a listing to be bookable.** Without payouts a client could pick a time and pay, and checkout would fail at Stripe. A new listing without payouts is left not bookable (nothing written, no Nylas call); an already-enabled listing whose coach has lost `stripeConnected` has `calendarBookingEnabled` set to false (everything else kept, so switching it back on is an ordinary sync) and is reported to Sentry once, code `nylas-booking-disabled-no-payouts`. Payout status is part of the signature, so adding payout details is picked up by the next 60-second loop with no other action. `stripeConnected` is a user attribute (not in the profile): the loop reads it from the included author, `sync-me` and the callback from the current user. If it cannot be read (`undefined`) the listing is left exactly as it is, so a missing attribute can never switch off a working listing. Listings enabled before this (the Test Session) keep their setup: when the only difference is the new key, they are re-stamped and nothing else is touched (dry run against both Dev listings: `adopted`, one key written).
  - **Only published session listings** (event type `signature-session`) of coaches with a grant are touched. A coach whose grant has stopped working is not detected; the listing stays as it was.
  - **A failing listing is reported to Sentry (`nylas-ensure-bookable-failed`) and retried at most every 10 minutes**; a missing `BOOKING_PROCESS_ALIAS` pauses the loop with one log line.
  - The loop compares state rather than following Sharetribe events because Dev keeps events for only 7 days. Fine at dozens of coaches; past a few hundred listings, switch the query to events with a stored cursor.
- **Coach-facing booking setup (client side).** Account settings > Calendar (`src/containers/CalendarSettingsPage/`, coaches only) holds the connect button and the **working hours** form: day toggles, one start and end time (half-hour steps), and a timezone, default Mon-Fri 9:00-17:00 in the browser's zone. Saving writes `privateData.bookingHours` on the coach's own user with the stock profile update, then calls `POST /api/nylas/sync-me`; if that call fails the hours are still saved and the server's loop applies them within a minute. `src/util/bookingHours.js` mirrors the server's validation (`server/api/nylas/hours.js` is the authority).
  - **A fixed-length session's sidebar depends on who is looking** (`OrderPanel`, `SessionSetupCard`). The listing's author sees one setup card, "Clients can't book this session yet", with two steps: connect a calendar (`/account/calendar`) and add payout details (the stock `StripePayoutPage`); a done step shows a tick and no button, and the card is not rendered once both are done (a plain "we're setting this up" line shows while the server finishes, normally under a minute). Everyone else sees the plain line "This coach isn't taking bookings yet." until the server has set the listing up. Neither is the error red. The stock "add your payout details" banner is not shown on fixed-length session pages (`ListingPage.shared.js`); it stays on every other listing. The card's promise is true because the server also requires payout details (next bullets): a listing goes live within a minute of the second step being done, whichever comes last.
  - **The AVAILABILITY step is gone from the listing wizard for fixed-length sessions** (`tabsForListingType`: Details, Pricing, Photos), and publishing is not gated on an availability plan; the server writes the plan the listing still needs (without its timezone no booking form renders). The check reads `listingTypeConfig.transactionType.unitType`: the hosted asset has `unitType` at the top level of a listing type, but `configHelpers.restructureListingTypes` moves it under `transactionType`, and the first version of this check read the hosted shape and so hid nothing on the deployed site. The test now builds the config through `mergeConfig` from the listing type exactly as Console serves it.
- **A coach connecting a different calendar gets a new Nylas grant, and `grantChange.js` re-points their listings.** Nylas matches an authentication to an existing grant by email address ([grant lifecycle](https://developer.nylas.com/docs/dev-guide/best-practices/grant-lifecycle/)), so reconnecting the same Google account keeps the grant id and the callback does nothing extra. A different account is a new grant; a Scheduler configuration lives under its grant and cannot be moved, so `server/api/nylas/grantChange.js` re-syncs each of the coach's calendar listings onto the new grant (fresh configurations, the new account's default calendar and timezone, same event type, notice and process alias) and keeps the old ids in `publicData.nylasPreviousConfigurationIds`. It always reports to Sentry with code `nylas-grant-changed`, listing the sessions still booked on the old calendar: those cannot be cancelled or rescheduled from Revie any more, because the listing now names the new configuration. The old configurations are left in place on the old grant.
- **Google login asks for `openid`, `userinfo.profile` and `userinfo.email` only** (`server/api/auth/google.js`; the template's retired `plus.login` was removed on Nov 10). `openid` is explicit because the callback reads the `id_token`. The Google login OAuth client is separate from the one Nylas uses for calendars.
- **A coach deleting a session's event from their own Google Calendar is a calendar notification, not a booking one** (found Nov 11, 2026: the booking stayed Accepted, nothing was refunded). Nylas's `booking.cancelled` fires only for a cancellation made *through the Scheduler* (our cancel button); a deletion in Google is reported as `event.updated` with the event's `status` set to `cancelled` (Google keeps a deleted event as a cancelled one, and reports `event.deleted` for other providers). The webhook destination therefore has to be subscribed to **`event.updated` and `event.deleted`** as well as the four `booking.*` triggers (a Nylas dashboard setting, not code). `calendarEventSync.js` handles them: it matches the event to a booking **only by the grant id and event id stored when the booking was made** (table `nylas_booking_events`; never by title or time), drops everything else before any other work (these notifications arrive for every event on every connected coach's calendar), and a match **waits five minutes before it cancels anything** (next bullet), then goes through the same `processBookingCancelled` as `booking.cancelled` (no client note = the coach cancelled = full refund at any time, Sharetribe's cancellation emails, `cancelledBy: provider`). Idempotent: a booking already cancelled is dropped, and Sharetribe refuses a second transition, so duplicates and the Scheduler's own `booking.cancelled` for the same booking cannot refund twice.
  - **A deletion is not believed for five minutes (accidental deletions).** A cancelled/deleted notice for a Revie event inserts a row in `nylas_event_cancellations` (due in five minutes; a repeat does not move the time; a later deletion after a restore starts a new wait). The sweeper's 60-second tick (`processDueEventCancellations`) claims due rows with `FOR UPDATE SKIP LOCKED` and a lock that expires by itself, so a restart or deploy during the wait loses nothing and two workers never act on one row. For each it reads the event again from Nylas (`GET /v3/grants/:grant/events/:id?calendar_id=…&show_cancelled=true`; 404 counts as gone): **back and not cancelled** = the coach undid it, nothing happens and it is logged once (a notice that it is confirmed again ends the wait at once); **still cancelled or gone** = the coach-cancel path runs. If the booking was already cancelled some other way (our own cancel button's `booking.cancelled` is never delayed, and the deletion it causes echoes back as a calendar notice) nothing more happens. A booking marked cancelled whose refund failed is **not** treated as finished: the transaction's own state decides, so a failed refund is retried (after a five-minute pause, reported to Sentry as `nylas-event-cancel-failed`) rather than dropped.
  - **A guest (the client) cannot cancel a session from their calendar.** Only the coach's grant is watched. A client declining the invitation changes the guest list on the coach's event, whose `status` stays `confirmed`, so the notice is ignored; a client deleting their own copy produces nothing we receive, and an event id seen under any other grant never matches a booking. Both are tested.
  - **Which event id is stored, and how it is kept right.** An id can come from three places: the response to creating the booking, the booking notices themselves (`booking_info.event_id`, on `booking.created` and `booking.rescheduled`), or reading the booking back from Nylas (`GET /v3/scheduling/bookings/:id` with a session). Only the last two are Nylas's own word, and are stored with `verified = true` (`nylas_booking_events.verified`); a verified row is never replaced by an unverified write. `eventIdBackfill.js` runs from the sweeper's tick and reads back every active upcoming booking whose id is missing or unverified, storing Nylas's answer under the booking's own grant, so a wrong or stale id heals within minutes. A booking that cannot be resolved is tried three times, five minutes apart, then given up on **once, with one log line, and stays given up across restarts** (`nylas_event_lookups`, in Postgres); cancelled and past bookings are never looked at.
  - **A deletion that matches no stored id is not dropped.** If the notice is plainly a cancellation (or has no status), `calendarEventSync.findBookingByLookup` reads back each of *that grant's* active upcoming bookings from Nylas (at most once every 30 seconds), corrects what is stored, and matches on Nylas's answer. It never searches other grants' bookings: the same Google event carries the same id in every guest's copy, so an id seen in someone else's calendar (a coach who is another coach's client, say) must never be taken for the organiser's event.
  - **What the logs say** (ids shortened to eight characters, nothing personal): `calendar event matched booking <id>, cancel scheduled for HH:MM UTC`; `calendar event did not match any booking (<trigger>, grant <id>, event <id>)` for a deletion or cancellation only (not for every edit of every event); `calendar event matched booking <id>, but it is <status>: nothing to do`. If a coach's deletion produces none of these, the notice never reached the handler.
  - **Volume:** every change to any event on a connected calendar now makes Nylas call the webhook once; each is a signature check and one indexed lookup, and only matches are logged. Fine at dozens of coaches.
- **Cancellation emails read the refund from transaction metadata, not from the total (release-5 templates).** The cancel transition refunds in full and Sharetribe then reports `payin-total` as 0, but the email is rendered after that, so release-3/4's "Your refund of {amount}" always said 0.00. Before running `transition/cancel`, `bookingSync.processBookingCancelled` writes `cancelledBy`, `refundAmount` (decimal, in the currency's own decimals) and `refundCurrency` to the transaction metadata; the email reads `metadata.refundAmount` and falls back to "Your refund is on its way" with no amount if it is missing (an operator cancelling from Console). `metadata` and camelCase keys are readable in email templates (`tx-line-items` has no way to tell a reversal from an original item: its documented fields are only `code`, `unit-price`, `line-total`, `include-for`, `quantity`, `percentage`, and the Handlebars set has no comparison helpers beyond `eq`, so summing line items in the template is not possible). The late-cancel emails use `payin-total` (what they were charged) and `payout-total` (what the coach will be paid), which are correct there because nothing is refunded. A coach-cancelled email (`metadata.cancelledBy` = `provider`) gets its own heading, wording and "Find another time" link to the listing (`/l/<listing id>`).
- **Email button colour comes from Console, not the templates.** Every Sharetribe template reads `design/branding.json` → `marketplaceColors.notificationPrimaryButton` (fallback `#6938EF` in the template). Dev's is `#ff9352` (our warning orange); it should be `#310416` (Console → Design → Branding, the email button colour). Test and Live are changed at cutover (`docs/go-live-plan.md`).
- **Templates only reach a process by a push.** Changing `ext/transaction-processes/default-booking/templates/` does nothing until a new version is pushed with flex-cli and given an alias, and only transactions started afterwards use it (each keeps the version it started on). The cancellation email fix is release-5 (not pushed yet at the time of writing).
- **Reminders and reschedule confirmations are sent by Postmark, from Postgres, by the sweeper tick** (`server/api/nylas/sessionEmails.js`, `server/email/`). Everything else (booked, cancelled, late-cancelled, payouts, reviews) is Sharetribe's.
  - **Queue:** table `session_emails`, one row per email, keyed by kind + booking + recipient + the session time it is for (so asking twice does nothing). Confirmed sessions (the `booking.created` handler) get a reminder for the client and one for the coach, due 24 hours before the session time in `nylas_bookings`; under 24 hours ahead gets none. `booking.rescheduled` cancels the pending reminders, queues new ones from the new time and queues a confirmation to each person (old time from the notice's `old_start_time`, our own row as fallback). Any cancellation (`processBookingCancelled`: our button, the Scheduler, and the coach-delete path once its five-minute wait ends) cancels everything still pending; an accidental deletion keeps its reminders until the wait ends. A confirmed session that never got reminders (made before this, or its webhook could not queue them) is picked up by a backfill on the tick.
  - **Sent at most once:** the tick claims due rows with `FOR UPDATE SKIP LOCKED` and marks them `sending` in the same statement; nothing ever picks a `sending` row up again, so two workers or a restart cannot send one twice, and one a dying worker had claimed is not repeated (it stays visible as `sending`). A send that fails cleanly goes back to `pending` and is tried on the next tick, three tries in all, each reported to Sentry as `postmark-send-failed` (ids and the recipient's domain only), then `failed`. A reminder is skipped if the booking is no longer active, its session moved, or fewer than two hours remain; a confirmation older than six hours is skipped.
  - **Switch and token:** `POSTMARK_SENDING_ENABLED` (default `false` in `render.yaml`) must be exactly `true`, and `POSTMARK_SERVER_TOKEN` set; otherwise nothing is claimed and rows wait (scheduling goes on, so switching on later finds the reminders ready). Logs never carry a body or an address.
  - **Templates are hosted in Postmark** (aliases `session-reminder-client`, `session-reminder-coach`, `session-rescheduled-client`, `session-rescheduled-coach`), created once by `scripts/postmark-create-templates.js` from `server/email/templates.js` (it validates with Postmark first and never overwrites an existing template unless `--overwrite`), then edited in Postmark. The code sends an alias and a model (`sessionEmailModel.js`); a test checks every `{{variable}}` in the drafts is a field the model provides, so wording edits in Postmark must stay within those fields.
  - **Times are in the recipient's timezone:** the coach's is the listing's working-hours zone; the client's is `protectedData.clientTimeZone`, saved from the browser at checkout for calendar bookings. Bookings made before that was recorded have none: the email then shows the coach's timezone and says so. The Meet link is read from the calendar event at send time (event id from `nylas_booking_events`); if it cannot be read the email goes without it.
- **A client can move a session only while cancelling it would still be free (48 hours), enforced on the server.** `POST /api/nylas/reschedule-booking` calls `canClientReschedule()` (`scheduler.js`, a thin wrapper over `isFreeCancellation`, so the two cannot disagree) with the session's *real* start from our database, and answers 409 `reschedule-too-late` inside the window without touching Nylas; a row with no usable start is refused rather than guessed at. The new time must also meet the listing's own booking notice (`nylasMinBookingNoticeMinutes`, 24 hours by default; 400 `reschedule-too-soon`), because the slot picker's filter alone is a client-side convenience. `GET /api/nylas/booking-status` returns `rescheduleAllowed` (true/false/null) so the page can disable the button and say why. **Coaches are not limited**: they move the event in their own calendar, which arrives as `booking.rescheduled` and is applied as before.
- **Every move is noted on the transaction for the Activity list.** The `booking.rescheduled` handler appends `{at, fromStart, toStart, toEnd}` to `metadata.reschedules` (last 20; the same move delivered twice is not added twice; best effort, a failure is reported as `nylas-reschedule-note-failed` and never fails the webhook). `ActivityFeed.js` turns them into "The session was moved to ..." lines (`src/transactions/reschedules.js`), the same way it shows release-3 late cancellations. Nothing about *who* moved it is stored. After a client's own reschedule the "Your session" card shows "Moved to ..." at once and polls booking-status until the webhook has updated our row.
- **A cancellation with no start time never charges the client.** `isFreeCancellation()` used to read a missing start (`new Date(null)` is 1970) as "session long past" and return *charged*. It now reports `nylas-cancel-start-missing` to Sentry and returns *free*; `processBookingCancelled` does the same with the booking and transaction ids in the alert (it used to throw and retry forever). An *unparseable* start, or a missing cancellation time, still throws. A client reschedule with no start time is refused, not allowed.
- **A cancel that Sharetribe refuses is now loud.** If `transition/cancel` gets a 409 and the transaction's last transition is not `transition/cancel` (for example `transition/complete`, after the payout), the client has not been refunded; `processBookingCancelled` reports it to Sentry with the tag `nylas-cancel-refused` (transaction, booking, last transition) instead of treating it as "already cancelled". A genuine redelivery, where the last transition *is* `transition/cancel`, stays quiet.
- **Who cancelled decides what happens (release-4, decided Nov 5).** The client's cancel button first writes `cancelRequestedBy: 'customer'` to the transaction metadata (and refuses to cancel if it cannot), because the `booking.cancelled` webhook cannot tell a client's cancellation from a coach deleting the event in their calendar. The webhook then: **no note = the coach cancelled** → `transition/cancel` (full refund, at any time) and `cancelledBy: provider`; **note and more than 48 hours out** → `transition/cancel` and `cancelledBy: client`; **note and inside 48 hours** → `transition/late-cancel` (operator, `accepted → late-cancelled`, no refund action, emails to both sides), `cancelledBy: client` and `lateCancelledAt` in the metadata. `transition/complete-late-cancelled` is time-triggered at booking end + 2 days (`stripe-create-payout`, "money paid" email to the coach) into `late-cancelled-completed`; neither state has a review transition or review email. `late-cancel` deliberately does not run `cancel-booking`, so the booking record the payout timer reads is untouched.
- **Release-3 transactions have no `late-cancel`.** Sharetribe answers a transition the process does not have with a 409, the same as "already made", so the webhook re-reads the transaction's last transition to tell them apart; for a release-3 transaction only the metadata is written and the UI (`src/transactions/lateCancellation.js`) shows it as late-cancelled. Their review emails still go out. A transaction keeps the process version it started on, so this fallback is needed until the last release-3 transaction is over.
- **The `BookingCanceledToProvider` email no longer says the client cancelled** (key `ContentNeutral`), because `transition/cancel` now also runs when the coach cancels.
- **Several templates have no body for our bookings.** The coach's confirmation ("operator accepted") used to branch only on `unitType` hour, day or night, so a `fixed` session printed a title and no sentence. Release-3 adds the `fixed` branch (`BookingOperatorAcceptedRequest.ContentForFixed`, "{customer} booked {session}, {start} to {end}. It's already on your calendar, so there's nothing for you to do."). The client's "accepted", "declined" and "expired" and the coach's "money paid" emails handle `fixed`. Money-paid still prints the original time after a reschedule.
- Times in these emails come from the transaction's booking, which Sharetribe never updates, so they show the original time after a reschedule.
- Account emails (verify email, password reset, user approval) are Sharetribe built-ins configured in Console, not in the repo.
- Unverified: Google/Nylas may also send its own calendar invitation to the client when the booking event is created.
- **Nylas's own emails are off (Oct 28).** Every configuration is created and updated with `event_booking.disable_emails: true`, because a cancel produced two emails for each person. The calendar provider's invitation is separate and still goes out. The only cancellation email seen in testing came from Nylas, so until release-3 nobody got one from Sharetribe.
- **Console email texts shadow the templates' inline defaults** for any key Console already has, exactly as marketplace texts shadow `en.json`. `BookingFailed.*` and `BookingExpiredRequest.ContentForFixed` are release-2 keys Console does not have yet.

## Session lengths and price variations
- **The template (12.3) fully supports price variations for the `fixed` unit type.** The coach editor offers up to 20 variants per listing, each with a name, a price and a length (15-minute steps, up to 12 hours), stored in `publicData.priceVariants` as `{name, priceInSubunits, bookingLengthInMinutes}`. Dev's `signature-session` listing type has `priceVariations.enabled: true`.
- **Our booking form already knows about variants.** `NylasBookingForm` shows the variant picker, sends `priceVariantName` through checkout (it lands in the transaction's `protectedData`), and filters the slot list to the chosen variant's length in the browser.
- **But no length other than 60 minutes can be booked today.** Nylas returns slots at the configuration's fixed duration (`duration_minutes`, 60 in `scheduler.js`), so a 30, 90 or 120 minute variant finds no slots.
- **Nylas can't offer several lengths from one configuration.** Probed against the live API: a private configuration's availability endpoint rejects `duration_minutes` and `duration` (HTTP 400, "invalid path"). Nylas's docs say a booking's start and end "must correspond to a valid time slot returned by the Scheduling Availability endpoint using the same Configuration", so longer slots can't be built by joining shorter ones. Duration is one fixed value per configuration. The way through is one Nylas configuration per length. Nylas documents no limit on configurations per grant or application.
- **One Nylas configuration per session length (built Oct 28).** `publicData.nylasConfigurationIds` is `{ "<minutes>": id }`; the old single `nylasConfigurationId` is still written (always the 60-minute one) and still read as the "60" entry, so listings enabled earlier keep working. `server/api/nylas/bookingConfig.js` is the only file that knows both shapes. `resolveBookingTarget` picks the configuration from the booking's own length; the availability endpoint takes `priceVariantName` (booking form) or `lengthMinutes` (reschedule); reschedule refuses a new time of a different length. `enableListing` syncs one configuration per distinct variant length and keeps configurations for lengths no longer sold (a booked session can only be cancelled through its own). **If a coach adds a variant length, they must re-run enable for the new length to have times.** Slots start on the hour and half hour (`interval_minutes` 30, `round_to` 30). The Dev `length` field has not been removed yet.
- **Pricing no longer falls back silently** (branch `payment-failure-recovery`). `server/api-util/bookingVariantCheck.js`, called at the top of `transactionLineItems`, refuses a fixed-length booking whose `priceVariantName` is missing, unknown, or whose length differs from the variant's `bookingLengthInMinutes` (400 on initiate, the line-items estimate and transition-privileged). Before this, a missing name charged the base price (the lowest variant) and nothing compared lengths. It applies to any fixed listing with price variations switched on.
- **Live today (read from the public site, 46 listings, 47 variants):** 60 minutes ×24, 90 ×16, 75 ×4, 45 ×2, 30 ×1, none at 120. 45 and 75 minutes exist, not only multiples of 30. Live listings carry `startTimeInterval` and `timezone`, and no `calendarBookingEnabled`.

## Sharetribe constraints that shape design
- **Console marketplace texts shadow the repo's translations.** The app merges `{...en.json, ...hostedTranslations}` (`src/app.js`), and Dev's hosted `content/translations.json` holds a copy of essentially every template key (1,397). So changing the *value* of an existing key such as `TransactionPage.default-booking.customer.declined.title` in `src/translations/en.json` changes nothing on Dev: Console's value wins. Revie-specific text therefore goes under **new keys Console does not have** (e.g. `ManageCalendarBooking.*`, `NylasBookingForm.bookButton`), and stock keys are changed in Console (in Test, then copied to Dev). The repo's value for a stock key is kept equal to the intended Console value so the two agree. Email texts behave the same way: `content/email-texts.json` overrides the inline defaults in a process's templates for any key it already has (`BookingAcceptedRequest.*`, `BookingExpiredRequest.Title/Subject`), so those are also changed in Console, with no process push.
- **Nylas rejects `cancellation_url` / `rescheduling_url` unless they contain `:booking_ref`.** With the hosted links hidden the URLs are formal only, so they are the Revie orders page plus `?booking=:booking_ref`.
- **A calendar listing's process comes from `BOOKING_PROCESS_ALIAS`.** `enableListing` writes it onto the listing in the same update as the configuration ids and refuses to enable if it is unset; initiate refuses a calendar listing booked under any other alias. Dev: `default-booking/release-2` (in `render.yaml`). Production gets its own value at cutover.
- **The calendar event is edited after booking.** `eventDescription.js` writes the client's name and a link to that session's order page onto the event (the booking response carries `event_id`; the calendar id is `publicData.nylasCalendarId`, written by enable). Best effort: a failure is reported to Sentry and never fails the booking. Listings enabled before this have no `nylasCalendarId` until re-synced (`scripts/dev-resync-listing.js` on Dev).
- **Top-level data model is fixed:** users, listings, transactions, bookings, stock, reviews, messages, each extensible with extended data. No new first-class entities. Anything else needs our own database (Postgres on Render).
- **Users match to a coach but book a listing.** One coach has many Signature Sessions.
- **Sharetribe indexes listings, not users.** A "Browse coaches" page needs a deliberate architecture.
- **Search is filter-based, not relevance-ranked.** Keyword plus enum / multi-enum / number / boolean filters. Any "sorted by fit" is our own logic after retrieval.
- **Transaction processes** are ours to define from a fixed vocabulary of actions. Custom logic runs asynchronously via Events and the Integration API.
- **Reviews and messages attach to transactions.** Coach-level ratings must be computed.
- **Coach subscriptions are Stripe Billing**, separate from the Stripe Connect marketplace flow.
- **Sharetribe booking records can't be changed after creation.** A rescheduled session's real time lives in our Postgres table, not on the transaction.
- **Coaches no longer accept calendar bookings** (client changes deployed to Dev; process release-2 pushed to Dev only). Release-2 removes the provider `accept`/`decline` transitions. The client shows no Accept/Decline unless a transaction's `nextTransitions` still allows it (older release-1 transactions), no inbox badge (`statesNeedingProviderAttention` is empty), and `ACCEPT`/`DECLINE` stay in the client state graph for old transactions.
- **Process versions (as of 2026-10-28, `npx flex-cli process list --process default-booking --marketplace <id>`):** Dev (`revie1-dev`): version 1 `release-1` (4 transactions), version 2 `release-2` (6), version 3 `release-3` (0). Test (`revie1-test`): version 1 `release-1` (4), version 2 `release-2` (0), version 3 `release-3` (0). **Live (`revie1`) has had nothing pushed and must not until cutover.** A new version only affects new transactions; each transaction keeps the version it started on. Release-3 = release-2 plus the cancellation emails and the coach's fixed-length body. The Dev Test Session listing is on release-3; `BOOKING_PROCESS_ALIAS` decides what newly enabled listings get.
- **Release-4 (Nov 5, 2026):** pushed to Dev (`revie1-dev`) and Test (`revie1-test`) as version 4 with alias `release-4` (0 transactions on each when pushed); the Dev Test Session listing moved from release-3 to release-4 the same day. Live untouched. `render.yaml` now carries `BOOKING_PROCESS_ALIAS=default-booking/release-4`.
- **Release-5 (Nov 12, 2026):** release-4's graph with the corrected cancellation emails. Pushed to Dev only (`revie1-dev`, version 5, alias `release-5`); **not on Test or Live**. The three enabled Dev listings (Test Session, Test Session 1, Test 2) were moved from release-4 to release-5 and their sync signatures re-stamped in the same step (the stored setup already matched, so only `nylasSyncSignature` was written), and the reconcile loop reports them `unchanged`. An enabled listing keeps its own alias in the loop whatever `BOOKING_PROCESS_ALIAS` says (the signature uses the listing's alias), so the loop can never move one back; only new listings take the environment value. `render.yaml` now carries `BOOKING_PROCESS_ALIAS=default-booking/release-5`. Transactions already started stay on release-4 and use its templates.
- **A new transaction uses the LISTING's `publicData.transactionProcessAlias`, not the listing type's.** The listing type's alias is only copied onto a listing when it is created, so changing the type in Console leaves existing listings on release-1. Existing Dev listings must be switched individually (`scripts/dev-listing-test-helper.js use-release-2`). Console's listing type cannot be set to a specific version (it only offers the default processes), so the listing type stays on release-1 and the alias has to be written onto each listing by other means; until that is built, the Dev "Test Session" listing was switched by hand with the helper.
- **Sharetribe validates bookings against the listing's `availabilityPlan`** when a booking is created, and `OrderPanel` needs `availabilityPlan.timezone` to render any booking form. `enableListing` therefore overwrites each calendar listing's plan with a 24/7 one carrying the calendar's time zone. Anything a coach enters in the stock Availability tab is discarded when that runs.
- **Console branding overrides code.** Hosted branding (colors, logo) is applied inline on `<html>` and beats the stylesheet; the repo's `configBranding.js` is only the local fallback.

## What the inbox count and the topbar dot count
Not unread messages. `fetchCurrentUserNotifications` (`ducks/user.duck.js`) asks Sharetribe for transactions in a list of **state names** that is merged across all registered processes (`getStatesNeedingProviderAttention` / `...CustomerAttention` in `transactions/transaction.js`). The booking process lists none of its own (`statesNeedingProviderAttention = []`, no customer list), so the count comes from a name collision: the unused negotiation process lists `delivered` for customers, which matches a booking's `delivered` state. In practice: **the client's completed sessions that they have not reviewed yet**. A coach's count is always 0. It drops when the client leaves a review. The merge by name is a known template limitation ("subject to problems if one process has a state named similarly"), so removing the negotiation process from `PROCESSES` would silently turn the count off.

## Reading Render's logs, and two traps found on Nov 5
- **Render's request log lines do not contain the path in their text** (`clientIP=… requestID=… responseTimeMS=… userAgent=…`); the method, path and status are in the log entry's *labels*. Searching the text for "/api/nylas/webhooks" finds nothing even when Nylas is delivering. Our own lines are what to search for: `[nylas] webhook POST /api/nylas/webhooks signature=valid trigger=booking.created` (added Nov 5) and `[nylas] booking.created -> accepted`. The Render API (`/v1/logs`, read-only) returns the labels.
- **The sweeper's age cutoff now works (fixed Nov 5).** `lastTransitionedAtEnd` is documented but silently ignored by the Integration API (the same 12 transactions came back for any value, even a made-up parameter), so the sweeper used to grab every paid booking on its next tick. `findPaidUnconfirmedTransactions` now filters on `lastTransitionedAt` in our own code, with a two-minute cutoff on the 60-second tick: the sweeper is a backstop for a closed tab or crashed worker and no longer races the browser's call or the order page's retry. `lastTransitions` is honoured (tested), only the time filter was not.
- **`create-booking` refused every real customer from Oct 27 to Nov 5, and that was invisible.** The caller check (added with the recovery work, PR #6) compared the logged-in user with `tx.relationships.customer`, but a Marketplace API transaction only carries a relationship's reference when it is requested with `include`, so the customer was always "missing" and the browser's fast path always got a 403. Bookings still worked because the sweeper (which had no working age gate) booked them on its next tick, 0 to 60 seconds after payment; the "5 seconds" seen on Nov 4 was a lucky tick, not the US app. Before PR #6 there was no such check and the fast path worked (Sep 13). Now `loadCalendarBookingTransaction` includes `customer`, and `verifyCaller` settles a still-missing relationship from the caller's own orders instead of treating it as "not the customer"; a different user is still refused. The order page also asks once more at ten seconds if the booking is still unconfirmed (safe: a database claim per transaction).
