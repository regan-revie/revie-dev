# Tech constraints

Listing fields, transaction processes, integrations and other technical
constraints the planning project needs to know about. Do not put secrets in
this folder; it is synced to Claude.ai.

*Last checked against the repo: 2026-10-20. Claude Code keeps this current.*

## Stack
- **Platform backend:** Sharetribe. On the **Pro** plan, which lets us build with Extend features in Dev but not publish custom code live until we upgrade to **Extend** ($299/mo).
- **Platform frontend:** customized Sharetribe Web Template (React/Node), self-hosted. Repo `regan-revie/revie-dev`. Dev deploy on Render (`revie-dev.onrender.com`): web service on the Starter plan plus Postgres (`revie-dev-db`), both in Frankfurt.
- **Marketing site:** Webflow. Not being rebuilt; out of scope. The platform should still feel like the same brand when someone clicks through from it.
- **Go-live:** January 1, 2027 (includes the upgrade to Extend).
- **Implementation:** Regan with Claude Code.

## Environments
Three Sharetribe environments, each with its own hosted configuration (listing types, branding, logo, Stripe), so they drift silently:
- **Dev** (flex-cli marketplace id **`revie1-dev`**; `revie_dev` is only the marketplace's display name, and flex-cli rejects it): the only one that supports custom code; what this repo develops against. Private marketplace. Use `npx flex-cli ... --marketplace revie1-dev` (flex-cli is not installed globally; Regan is logged in, and the key must never be read or printed).
- **Test:** a no-code preview meant to mirror Live. Console config changes are made here and copied to Dev and Live.
- **Live:** production. A public marketplace, currently running Sharetribe's hosted frontend, not this codebase.

## What's already built (platform)
- **Nylas calendar integration:** coaches connect Google/Outlook; availability comes from their real calendar. Booking, payment capture and confirmation work end to end (first real booking 2026-09-13).
- **Working hours:** the availability endpoint reads `publicData.nylasOpenHours` per listing (one window of days + start + end) and filters slots by it. **Nothing in the repo writes that field**, so coaches have no way to set working hours; it has to be set by hand. A coach with no hours set is simply bookable at any time the calendar is free.
- **No coach-facing UI for the Nylas flow exists.** The server endpoints are there (`/api/nylas/connect`, `/callback`, `/enable-listing`), but nothing in `src/` calls them: a coach cannot connect a calendar, choose one, or switch a session to calendar booking from the product. Only the client-side booking, checkout and cancel/reschedule UI is built.
- Render service with Postgres, verified webhook path with HMAC signature checks
- Custom booking UI replacing Sharetribe's, plus client cancel/reschedule (built; not yet exercised live end to end)
- **Booking creation after payment is now server-owned and recovers from failure** (branch `payment-failure-recovery`, not yet deployed). `server/api/nylas/bookingRecovery.js` `ensureBooking()` takes a Postgres claim (`nylas_booking_attempts`), makes up to two attempts (a network error, 408, 429 or 5xx is retried; "slot taken" or a rejected key is not), waits about 10 seconds for a late `booking.created` webhook, then runs `transition/operator-decline` (full refund, cancels the uncaptured card authorisation per Sharetribe's documentation) and logs to Sentry with the code `nylas-booking-failed-declined`. A webhook arriving after a decline cancels the orphaned Nylas booking (`nylas-orphan-booking-cancelled`). A 60-second sweeper in the web service (`server/jobs/`) handles paid bookings older than 3 minutes that the browser never reported. Sentry only records anything if `REACT_APP_SENTRY_DSN` is set in Render, and an alert rule is still needed for the email to Regan. Unproven end to end: the SQL has not been run against a real Postgres, and the Stripe test-mode check and the Dev process rollout are still to do.
- Google SSO, Integration API wired up
- **Brand tokens in `src/styles/revieTokens.css`**, imported after `marketplaceDefaults.css`. Lives on branch `revie-design-tokens` and is not yet committed or merged to `main`.

- **A client declining the calendar invite is told their session is still booked (2026-11-25)** (`server/api/nylas/calendarEventSync.js`, `sessionEmails.js`).
  - **Why:** clients decline, or delete, the coach's invite thinking it cancels the session, then are charged for a no-show. Declining changes only their copy and their answer on the guest list; the booking, the calendar event and the payment are exactly as they were. Nothing here cancels or refunds anything.
  - **Detection:** the Nylas `event.updated` notice we already receive for the coach-delete logic (no new webhook trigger). It goes through the **same own-copy gate** first: the notice must come from the booking's own coach grant and the calendar the booking was made on, so a guest's own copy (a client who is also a coach has the same event id on *their* grant) and any other event are ignored. The guest list is read from the notice, or from Nylas if the notice carries none. A guest counts only if their status is `no` **and** their email is the booking's client's (the Sharetribe customer's email, which is the guest email the booking was made with, compared ignoring case and spaces); the coach, or any other guest, declining is ignored. Sharetribe is only asked for the client's email when somebody has declined at all. A cancelled event is the cancellation path, never a decline email; a booking that is not `created`/`rescheduled` is ignored.
  - **Once per booking:** a row in `session_emails` keyed `declined-invite:<booking>:client` (no time in the key), so a repeat notice, declining again, or accepting then declining again, queues nothing. Queued only for a session still ahead; the send (sweeper tick, so within about a minute) re-checks the booking is still active, the session has not started and the transaction is still a live one (`operator-accept` or `update-booking`), and skips otherwise. Not held back as stale: it is as true hours later as now, until the session starts. A reschedule does not cancel it (still booked, at the new time); cancelling the booking does.
  - **Only to the client.** Nothing to the coach (Google already tells them). Template `calendar-invite-declined-client`, subject "Your session is still booked"; one button "See your booking"; says cancelling within 48 hours is charged in full; deliberately does not suggest messaging the coach.
  - **Failure:** three tries, then Sentry `postmark-declined-invite-failed` with the booking id and the address's domain only. Nothing is claimed or sent while `POSTMARK_SENDING_ENABLED` is off; it goes out once it is on if the session is still ahead.
  - **Not proven against Google:** that Google reports an invitee's decline (and an invitee *deleting* the invite, which Google answers with a decline) to Nylas as an `event.updated` carrying `participants[].status: 'no'`. See the HANDOFF's test steps.
- **A coach's Google connection can break, and now the platform notices (2026-11-24)** (`server/api/nylas/grantStatus.js`, `grantHealth.js`).
  - **What breaks it:** the coach removes Revie's access in their Google account, Google asks for a fresh sign-in, or the Nylas grant is deleted. Before this nothing noticed: the Calendar page said "connected", sessions stayed bookable, and a client could pay for a time that could not go on the calendar.
  - **State:** on the coach's own user, in **privateData** (the coach and the Integration API can read it, no one else): `calendarStatus` (`connected` | `reconnect_needed`; missing means connected), `calendarBrokenAt`, `calendarBrokenReason`, `calendarReconnectEmailedAt`. The public `calendarConnected` flag is left alone; the UI reads `calendarStatus` first (`src/util/calendarConnection.js`).
  - **Three ways it is noticed:** (1) Nylas webhooks `grant.expired` and `grant.deleted` (add them to the destination, see the HANDOFF; the receiver finds the coach whose *stored* grant it is, so an old grant of a coach who has since connected a different account is ignored); (2) a **daily check** of every coach's grant (`GET /v3/grants/:id`, `grant_status: invalid` or 404 means broken), which also runs a few minutes after each boot; (3) the reconcile loop looks at every coach already marked, every minute (below). A Nylas outage, a rate limit or a rejected API key is "unknown", never "broken". If the daily check finds **every** checked grant broken (three or more) it flags nobody and reports `nylas-grant-check-suspicious` instead: that pattern is a wrong Nylas region or key, not coaches (the EU/US move would look exactly like this).
  - **What it does when it finds a break** (idempotent, under a per-coach lock): marks the coach, switches off `calendarBookingEnabled` on their published sessions at once, reports to Sentry with the tag `nylas-grant-expired` and **only the coach id and the reason** (no grant id, token or email), and sends the one email. The reconcile loop (`ensureBookable.js`) keeps those sessions off every minute thereafter: a coach with `reconnect_needed` is "not connected" for booking purposes, so clients see "This coach isn't taking bookings yet" and the availability endpoint returns no times.
  - **No new booking can start:** `initiate-privileged.js` refuses a booking (and the price preview) on a calendar session that is set up but switched off (`calendar-not-bookable`, a 400 so it is not read as "time just taken"), however old the client's page. **Existing bookings are not touched**: nothing here reads or changes a transaction.
  - **One email per break, not daily:** `calendarReconnectEmailedAt` is stamped when it is sent and cleared by a reconnect. Driven by state, so a send that failed is retried (at most every 10 minutes) and a duplicate webhook or a daily check cannot send a second. Nothing is sent, or stamped, while `POSTMARK_SENDING_ENABLED` is off; it goes out once it is on if the break is still there. If the send succeeds but writing the stamp fails, a later tick sends it again (rare, and better than never telling her). The template is `calendar-reconnect-coach` ("Reconnect your calendar to keep taking bookings"); its button goes to `/account/calendar`, not straight to Google, so it works when she is logged out.
  - **Reconnecting clears it:** the Nylas callback writes `calendarStatus: 'connected'` and clears the other three, then sets her sessions up in the same request (bookable at once). If the grant starts working some other way, the reconcile loop's per-minute look clears it within the minute, with no second email. Reconnecting the same Google account keeps the same grant id.
  - **UI:** Calendar page "Reconnect needed" with a "Reconnect Google Calendar" button; the session setup card shows the calendar row as not done ("Reconnect your calendar", straight to the Google connect route).
- **Promo codes (2026-11-23): Revie-funded, out of Revie's commission only** (`server/api/promo/`, `server/api-util/lineItems.js`).
  - **The money, for a £100 session with 15% off:** the session line £100 (customer and provider), `line-item/promo-discount` -£15 (**customer only**), `line-item/provider-commission` -£20 (provider only, from the full price). Payin £85, payout £80, Revie keeps £5 before Stripe's fee. The coach is untouched because the provider commission is calculated from the session line alone; nothing needs "adjusting". Sharetribe needs payin ≥ payout (documented, and `assertPromoIsAffordable` checks it after rounding).
  - **Ceiling 15%, in code** (`MAX_PERCENT_OFF` in `rules.js`): refused at checkout, by the line-item builder and by the script, and never above the commission (compared in money, so a minimum-amount commission is respected). A row in the database above the ceiling is treated as not existing.
  - **Line items are set only at the two `privileged-set-line-items` transitions** (`request-payment`, `request-payment-after-inquiry`); nothing after recalculates them (Sharetribe warns that running it after the payment intent exists does not update Stripe). So the discount is fixed at the real initiate. `request-payment-after-inquiry` (`transition-privileged.js`) refuses a code. A full refund reverses every line, so the refund is what the client paid (£85); late cancel keeps the £85 and pays the coach £80; reschedule recalculates nothing. No process change, no new release.
  - **Tables** (created at boot by `promoStore.initSchema`, and by the script): `promo_codes` (code, percent_off, expires_at, max_total_uses, uses_so_far, max_uses_per_customer default 1, first_session_only, active) and `promo_redemptions` (code, customer_id, transaction_id, status reserved/paid/released, percent_off, checked_at).
  - **Use lifecycle:** reserved at the real initiate under a row lock (so two clients cannot take the last use), counting against both caps; tied to the booking once Sharetribe creates it; **paid** when the booking is accepted; **released** when payment expires (15 minutes), the booking is declined or expires, a reservation never got a booking (30 minutes), or the client is **refunded in full** (`transition/cancel`). A late cancel stays consumed. The reconcile loop (`reconcile.js`, 60 s) does this from Sharetribe's transition history, and re-checks paid uses every 5 minutes for 90 days. `uses_so_far` counts paid uses; `list` counts from the redemptions rather than trusting it.
  - **First session only:** from Sharetribe, with the **client's own session** (`transactions.query({only:'order'})`), so it can only read their own orders, covers bookings from before codes existed, and cannot be pointed at someone else. A booking counts when it reached `confirm-payment` and has no `cancel`, `operator-decline`, `decline` or `expire`; a late-cancelled one counts. A failed look-up counts as "has booked before". Our own reservations also block a second simultaneous first-session purchase.
  - **Attempt limit and wording:** 8 failed guesses per 10 minutes per user (in memory), then "Too many tries". An unknown or switched-off code always says "That code isn't valid." with no hint which; expired, used up, first-session-only and already-used are only revealed for a code that exists.
  - **Checkout:** `POST /api/promo/check` answers an Apply press at once (reserves nothing); the price preview and the real booking carry the code in the server-only `orderData` (never in the params sent on to Sharetribe) and the server re-judges everything. The code is judged from the client's own session; the percentage always comes from the database. The code field is hidden once a booking exists (its price is then fixed). The order breakdown shows "Promo discount (CODE)" for the client only; the coach never sees it.
  - **Database down:** applying a code says "try again"; booking without a code is unaffected.
  - **Listing page still shows the full price**: its estimate ignores codes; the discount appears at checkout.
  - **The "You're booked" email** shows "Session price", "Promo discount (CODE)" and "Total paid" when a code was used. Postmark's template must be updated once (`scripts/postmark-create-templates.js --overwrite --only booking-confirmed-client`), which **replaces any wording edited in Postmark for that one template**.
  - **Not yet proven on Sharetribe:** that its API takes this exact shape (customer-only negative line, payout below payin, `metadata.promo` on the initiate). `scripts/promo-line-item-spike.js` asks for a speculative initiate (no booking, no money) and prints the totals or Sharetribe's refusal. Run it first (see the HANDOFF).
- **Search never ends on an empty page (2026-11-18).** When a search finds fewer than 3 sessions (`FEW_RESULTS_LIMIT` in `SearchPage.duck.js`, read from Sharetribe's `totalItems`), the same request also fetches the 24 newest published listings, keeps those with `publicData.calendarBookingEnabled === true` that are not already matches, and shows up to 6 under "Other coaches you might like". "Bookable" here means the coach has enabled calendar booking on the session; it does not check live availability. **The extra query asks for exactly what the search results ask for** (`listingCardQueryParams` in `SearchPage.duck.js`: include author and images, the card's image variants, the card's listing fields, plus `publicData.calendarBookingEnabled` because fields are sparse), so a card renders from the fallback response alone; a first version omitted this and its cards showed "No image" and no coach name until the session had been opened once. If the search results' fields or variants change, change that one function and both follow. The extra query is made server-side inside the search thunk, so the sessions are in the first server-rendered page, and its failure resolves to an empty list rather than breaking the search. It is not filtered by the visitor's other filters and it is not paginated. When nothing matches and other sessions exist, the "couldn't find any listings" sentence is dropped and only the "Reset filters" button stays; with no other sessions to offer, the old message is unchanged.

## Emails
Every email today is a Sharetribe built-in. The default-booking process (`ext/transaction-processes/default-booking/`) sends:
- **At payment (`confirm-payment`):** release-1 emails the coach "You have a new booking request", the stock accept-or-decline wording. Process release-2 (in `ext/`, not yet pushed anywhere) removes it, so a coach is not emailed before the booking exists.
- **At `operator-accept`:** the client gets "Your booking request was accepted"; the coach gets an operator-accepted email.
- **At expiry / decline:** the client gets "request expired" or a failure email. In release-2 the failure email (sent by `operator-decline`) says the booking didn't go through and nothing was charged, and the expired email has a body for fixed-length sessions. The provider's "declined on your behalf" email is removed.
- **After the session (`complete`):** payout ("money paid") email to the coach and review requests to both.
- **Cancellation:** from release-3, `transition/cancel` emails the client (full refund on its way, amount from `payin-total`) and the coach (session cancelled). Release-2 sent nothing. Single instance only: with several Render instances a repeat could land on another one; the row check still catches it once the notice has updated our row.
- **"Your session" card copy (Nov 17).** The card shows the session time with the timezone named ("Fri, Nov 20, 2:30 – 3:30 PM (Pacific Time)", same naming as the confirm panel). Right after a reschedule *in this page visit* a success note sits under the time ("✓ Moved. We've emailed you both and updated your calendars.", Forest `--colorSuccess`, body size); on reload it is gone and the Activity list keeps the record. The 48-hour lock says: "This session is less than 48 hours away, so it can't be moved. You can still cancel, but you'll be charged in full." Nothing client-facing suggests messaging the coach to ask. The 24-hour reminder email used to say "Need to move it? Open your booking and choose Reschedule", which is wrong inside 48 hours (Reschedule is locked); it now says the session can't be moved and cancelling is charged in full. **Postmark hosts the templates, so the reminder wording only changes after `node scripts/postmark-create-templates.js --overwrite` is run.**
- **Choosing a new time opens a confirm dialog (a modal over the picker).** Clicking a time in the reschedule picker sends nothing; it opens the template's `Modal` ("Move your session?", *From* the current time, *To* the new one in the client's own timezone named as people say it, "Pacific Time", via `formatTimeZoneName` in `nylasSlots.js`). The picker stays underneath exactly as it was. "Confirm new time" is the only thing that sends the request (still one at a time, with "Moving your session…" inside the dialog); "Cancel", the close button and Escape close it. **Clicks on "Confirm new time" are ignored for 500 ms after the dialog opens** (a double-click on a time would otherwise confirm instantly; `CONFIRM_GUARD_MS`, measured with `Date.now()`). If the new time is less than 48 hours away the dialog adds: "This new time is less than 48 hours away. Once it's moved, you won't be able to move it again, and cancelling will be charged in full." Refusals show inside the dialog: a time no longer available (the confirm button goes; Cancel returns to the picker, whose times were quietly reloaded), the 48-hour rule (Cancel closes the dialog and the card goes back to its locked state), too soon (confirm stays); a cancelled session or one the coach is cancelling closes the dialog and shows on the card as before. The `Modal` needs `onManageDisableScrolling` (passed from `TransactionPage`) and the page's `#portal-root` (`public/index.html`); tests that open it add a `#portal-root` themselves.
- **Reschedule failures are classified and reported.** A Nylas failure is logged and sent to Sentry as `nylas-reschedule-failed` with Nylas's error type and message (no booking details), and answered with a code the page turns into a sentence: `reschedule-slot-unavailable` ("That time isn't available any more. Please pick another." and the free times are shown again), `booking-cancelled` ("This session has been cancelled."; Nylas 404 or a message mentioning cancel, or our own record being cancelled), `being-cancelled-by-coach` (below), `reschedule-too-late`, `reschedule-too-soon`, otherwise `reschedule-failed` (the plain "Something went wrong").
- **While the coach's deletion of the event is in its five-minute wait, the session is shown as being cancelled.** `GET /api/nylas/booking-status` returns `cancellationPending` (a pending row in `nylas_event_cancellations`); the page hides Reschedule *and* Cancel and says "This session is being cancelled by the coach. You'll get a full refund."; the reschedule endpoint refuses with `being-cancelled-by-coach`. Cancel is hidden because a client cancelling inside 48 hours would be charged for what the coach did, and `POST /api/nylas/cancel-booking` refuses too (409 `being-cancelled-by-coach`, the same sentence, from `coachCancelling.js`), **before** it writes the `cancelRequestedBy: customer` note, so the coach's cancellation can never be read as a client's and take the late-cancel path. If the coach puts the event back the buttons return by themselves.
- **The availability endpoint offers only times both Nylas and Sharetribe accept.** After Nylas's slots are cut by the coach's hours and the booking notice, each one is kept only if it fits inside one of Sharetribe's own time slots for the listing: one Marketplace API call, `timeslots.query` (the caller's session, `perPage: 500`, the window rounded out to whole days), asked at the same time as Nylas. Sharetribe builds those slots from the availability plan, exceptions and every *pending or accepted* booking, so a slot it holds for another booking (a late-cancelled session keeps its slot by design, the coach is paid; the five-minute wait after a coach deletes an event; a client mid-checkout; an old release-5 reschedule) is no longer offered. Adjacent day-by-day slots are merged so a session over midnight survives. **Fails open:** if the call errors, is rate limited, answers with nothing, or spans more than one page, every Nylas slot is kept (reported as `nylas-timeslots-failed` / `nylas-timeslots-paged`) and the friendly 409 at checkout is the backstop. Cached 15 seconds per listing and day-rounded window, concurrent requests sharing one call, so a slot taken in the last few seconds can be offered once more. When it hides something, Render logs `availability for listing X: left out N of M slot(s) that Sharetribe holds`. The Integration API has no time slots call, so this needs the caller's own session, as the endpoint's listing lookup already does. A client's own current slot is held too, but Nylas already treats it as busy, so nothing is lost for a reschedule.
- **The invitation a client gets is not followed by a second one (Sentry REVIE-PLATFORM-6).** Nylas takes an event's title and description only from the Scheduler configuration (its API reference has no per-booking description and no template variables), and a configuration is shared by every booking, so the client's name and their own session link cannot be set when the booking is made. They are written by one update straight after the booking (`eventDescription.js`). That update used to make Google send every guest an "Updated invitation" email, a duplicate of the one just sent, and was sometimes refused with 429. It now passes `notify_participants=false` (the guest's copy is updated silently; Microsoft ignores the setting and always notifies), sends the description and nothing else (no conferencing, times or participants), and a 429 is retried after 0.8 s and 2 s. A failure is reported (`nylas-event-description-failed`) and never fails or declines the booking. A real reschedule is a different call (the Scheduler's `PATCH /bookings`, `availability.js`), carries no notification override, and still tells the guest once.
- **Nylas can show a time that Sharetribe will refuse (Sentry REVIE-PLATFORM-8, a 409 on the price check).** The availability endpoint reads only the coach's calendar; Sharetribe separately holds each booking's slot until the booking is cancelled, declined or expired. So a client can pick a slot Nylas calls free and Sharetribe still holds, in these cases (each read from the code, not guessed): (1) **a late cancellation**: `transition/late-cancel` deliberately has no `:action/cancel-booking` (the payout is timed off the booking), so the slot stays held in Sharetribe although the calendar event is gone; (2) **the five-minute wait after a coach deletes an event**: the event is cancelled, so Nylas shows the slot free, while the booking stays accepted until the wait ends; (3) **two clients at once**: the first client's slot is held (pending booking) from checkout, but the Nylas booking only exists after payment; (4) **a reschedule of a release-5-or-earlier transaction** keeps holding the old slot (release-6 moves it); (5) **a booking whose calendar event was deleted before the matching fix in #29** and was never cancelled. Checkout now answers any such 409 on the price check or the real request with "That time was just taken. Please pick another." and a link to the listing page, which asks for the times afresh and starts with none picked (`isSlotTakenError` in `CheckoutPage/ErrorMessages.js`). The fix for (1)-(4) is `sharetribeSlots.js`, below.
- **A client can move a session only while cancelling it would still be free (48 hours), enforced on the server.** `POST /api/nylas/reschedule-booking` calls `canClientReschedule()` (`scheduler.js`, a thin wrapper over `isFreeCancellation`, so the two cannot disagree) with the session's *real* start from our database, and answers 409 `reschedule-too-late` inside the window without touching Nylas; a row with no usable start is refused rather than guessed at. The new time must also meet the listing's own booking notice (`nylasMinBookingNoticeMinutes`, 24 hours by default; 400 `reschedule-too-soon`), because the slot picker's filter alone is a client-side convenience. `GET /api/nylas/booking-status` returns `rescheduleAllowed` (true/false/null) so the page can disable the button and say why. **Coaches are not limited**: they move the event in their own calendar, which arrives as `booking.rescheduled` and is applied as before.
- **Every move is noted on the transaction for the Activity list.** The `booking.rescheduled` handler appends `{at, fromStart, toStart, toEnd}` to `metadata.reschedules` (last 20; the same move delivered twice is not added twice; best effort, a failure is reported as `nylas-reschedule-note-failed` and never fails the webhook). `ActivityFeed.js` turns them into "The session was moved to ..." lines (`src/transactions/reschedules.js`), the same way it shows release-3 late cancellations. Nothing about *who* moved it is stored. After a client's own reschedule the "Your session" card shows "Moved to ..." at once and polls booking-status until the webhook has updated our row.
- **A cancel that Sharetribe refuses is now loud.** If `transition/cancel` gets a 409 and the transaction's last transition is not `transition/cancel` (for example `transition/complete`, after the payout), the client has not been refunded; `processBookingCancelled` reports it to Sentry with the tag `nylas-cancel-refused` (transaction, booking, last transition) instead of treating it as "already cancelled". A genuine redelivery, where the last transition *is* `transition/cancel`, stays quiet.
- **Who cancelled decides what happens (release-4, decided Nov 5).** The client's cancel button first writes `cancelRequestedBy: 'customer'` to the transaction metadata (and refuses to cancel if it cannot), because the `booking.cancelled` webhook cannot tell a client's cancellation from a coach deleting the event in their calendar. The webhook then: **no note = the coach cancelled** → `transition/cancel` (full refund, at any time) and `cancelledBy: provider`; **note and more than 48 hours out** → `transition/cancel` and `cancelledBy: client`; **note and inside 48 hours** → `transition/late-cancel` (operator, `accepted → late-cancelled`, no refund action, emails to both sides), `cancelledBy: client` and `lateCancelledAt` in the metadata. `transition/complete-late-cancelled` is time-triggered at booking end + 2 days (`stripe-create-payout`, "money paid" email to the coach) into `late-cancelled-completed`; neither state has a review transition or review email. `late-cancel` deliberately does not run `cancel-booking`, so the booking record the payout timer reads is untouched.
- **Release-3 transactions have no `late-cancel`.** Sharetribe answers a transition the process does not have with a 409, the same as "already made", so the webhook re-reads the transaction's last transition to tell them apart; for a release-3 transaction only the metadata is written and the UI (`src/transactions/lateCancellation.js`) shows it as late-cancelled. Their review emails still go out. A transaction keeps the process version it started on, so this fallback is needed until the last release-3 transaction is over.
- **The `BookingCanceledToProvider` email no longer says the client cancelled** (key `ContentNeutral`), because `transition/cancel` now also runs when the coach cancels.
- **Several templates have no body for our bookings.** The coach's confirmation ("operator accepted") used to branch only on `unitType` hour, day or night, so a `fixed` session printed a title and no sentence. Release-3 adds the `fixed` branch (`BookingOperatorAcceptedRequest.ContentForFixed`, "{customer} booked {session}, {start} to {end}. It's already on your calendar, so there's nothing for you to do."). The client's "accepted", "declined" and "expired" and the coach's "money paid" emails handle `fixed`. Money-paid still prints the original time after a reschedule.
- Times in these emails come from the transaction's booking, which Sharetribe never updates, so they show the original time after a reschedule.
- Account emails (verify email, password reset, user approval) are Sharetribe built-ins configured in Console, not in the repo.
- Unverified: Google/Nylas may also send its own calendar invitation to the client when the booking event is created.
- **Nylas's own emails are off (Oct 28).** Every configuration is created and updated with `event_booking.disable_emails: true`, because a cancel produced two emails for each person. The calendar provider's invitation is separate and still goes out. The only cancellation email seen in testing came from Nylas, so until release-3 nobody got one from Sharetribe.
- **Console email texts shadow the templates' inline defaults** for any key Console already has, exactly as marketplace texts shadow `en.json`. `BookingFailed.*` and `BookingExpiredRequest.ContentForFixed` are release-2 keys Console does not have yet.

## Session lengths and price variations
- **The template (12.3) fully supports price variations for the `fixed` unit type.** The coach editor offers up to 20 variants per listing, each with a name, a price and a length (15-minute steps, up to 12 hours), stored in `publicData.priceVariants` as `{name, priceInSubunits, bookingLengthInMinutes}`. Dev's `signature-session` listing type has `priceVariations.enabled: true`.
- **Our booking form already knows about variants.** `NylasBookingForm` shows the variant picker, sends `priceVariantName` through checkout (it lands in the transaction's `protectedData`), and filters the slot list to the chosen variant's length in the browser.
- **But no length other than 60 minutes can be booked today.** Nylas returns slots at the configuration's fixed duration (`duration_minutes`, 60 in `scheduler.js`), so a 30, 90 or 120 minute variant finds no slots.
- **Nylas can't offer several lengths from one configuration.** Probed against the live API: a private configuration's availability endpoint rejects `duration_minutes` and `duration` (HTTP 400, "invalid path"). Nylas's docs say a booking's start and end "must correspond to a valid time slot returned by the Scheduling Availability endpoint using the same Configuration", so longer slots can't be built by joining shorter ones. Duration is one fixed value per configuration. The way through is one Nylas configuration per length. Nylas documents no limit on configurations per grant or application.
- **One Nylas configuration per session length (built Oct 28).** `publicData.nylasConfigurationIds` is `{ "<minutes>": id }`; the old single `nylasConfigurationId` is still written (always the 60-minute one) and still read as the "60" entry, so listings enabled earlier keep working. `server/api/nylas/bookingConfig.js` is the only file that knows both shapes. `resolveBookingTarget` picks the configuration from the booking's own length; the availability endpoint takes `priceVariantName` (booking form) or `lengthMinutes` (reschedule); reschedule refuses a new time of a different length. `enableListing` syncs one configuration per distinct variant length and keeps configurations for lengths no longer sold (a booked session can only be cancelled through its own). **If a coach adds a variant length, they must re-run enable for the new length to have times.** Slots start on the hour and half hour (`interval_minutes` 30, `round_to` 30). The Dev `length` field has not been removed yet.
- **Pricing no longer falls back silently** (branch `payment-failure-recovery`). `server/api-util/bookingVariantCheck.js`, called at the top of `transactionLineItems`, refuses a fixed-length booking whose `priceVariantName` is missing, unknown, or whose length differs from the variant's `bookingLengthInMinutes` (400 on initiate, the line-items estimate and transition-privileged). Before this, a missing name charged the base price (the lowest variant) and nothing compared lengths. It applies to any fixed listing with price variations switched on.
- **Live today (read from the public site, 46 listings, 47 variants):** 60 minutes ×24, 90 ×16, 75 ×4, 45 ×2, 30 ×1, none at 120. 45 and 75 minutes exist, not only multiples of 30. Live listings carry `startTimeInterval` and `timezone`, and no `calendarBookingEnabled`.

## Sharetribe constraints that shape design
- **Console marketplace texts shadow the repo's translations.** The app merges `{...en.json, ...hostedTranslations}` (`src/app.js`), and Dev's hosted `content/translations.json` holds a copy of essentially every template key (1,397). So changing the *value* of an existing key such as `TransactionPage.default-booking.customer.declined.title` in `src/translations/en.json` changes nothing on Dev: Console's value wins. Revie-specific text therefore goes under **new keys Console does not have** (e.g. `ManageCalendarBooking.*`, `NylasBookingForm.bookButton`), and stock keys are changed in Console (in Test, then copied to Dev). The repo's value for a stock key is kept equal to the intended Console value so the two agree. Email texts behave the same way: `content/email-texts.json` overrides the inline defaults in a process's templates for any key it already has (`BookingAcceptedRequest.*`, `BookingExpiredRequest.Title/Subject`), so those are also changed in Console, with no process push.
- **Nylas rejects `cancellation_url` / `rescheduling_url` unless they contain `:booking_ref`.** With the hosted links hidden the URLs are formal only, so they are the Revie orders page plus `?booking=:booking_ref`.
- **A calendar listing's process comes from `BOOKING_PROCESS_ALIAS`.** `enableListing` writes it onto the listing in the same update as the configuration ids and refuses to enable if it is unset; initiate refuses a calendar listing booked under any other alias. Dev: `default-booking/release-2` (in `render.yaml`). Production gets its own value at cutover.
- **The calendar event is edited after booking.** `eventDescription.js` writes the client's name and a link to that session's order page onto the event (the booking response carries `event_id`; the calendar id is `publicData.nylasCalendarId`, written by enable). Best effort: a failure is reported to Sentry and never fails the booking. Listings enabled before this have no `nylasCalendarId` until re-synced (`scripts/dev-resync-listing.js` on Dev).
- **Top-level data model is fixed:** users, listings, transactions, bookings, stock, reviews, messages, each extensible with extended data. No new first-class entities. Anything else needs our own database (Postgres on Render).
- **Users match to a coach but book a listing.** One coach has many Signature Sessions.
- **Sharetribe indexes listings, not users.** A "Browse coaches" page needs a deliberate architecture.
- **Search is filter-based, not relevance-ranked.** Keyword plus enum / multi-enum / number / boolean filters. Any "sorted by fit" is our own logic after retrieval.
- **Transaction processes** are ours to define from a fixed vocabulary of actions. Custom logic runs asynchronously via Events and the Integration API.
- **Reviews and messages attach to transactions.** Coach-level ratings must be computed.
- **Coach subscriptions are Stripe Billing**, separate from the Stripe Connect marketplace flow.
- **Sharetribe booking records can't be changed after creation.** A rescheduled session's real time lives in our Postgres table, not on the transaction.
- **Coaches no longer accept calendar bookings** (client changes deployed to Dev; process release-2 pushed to Dev only). Release-2 removes the provider `accept`/`decline` transitions. The client shows no Accept/Decline unless a transaction's `nextTransitions` still allows it (older release-1 transactions), no inbox badge (`statesNeedingProviderAttention` is empty), and `ACCEPT`/`DECLINE` stay in the client state graph for old transactions.
- **Process versions (as of 2026-10-28, `npx flex-cli process list --process default-booking --marketplace <id>`):** Dev (`revie1-dev`): version 1 `release-1` (4 transactions), version 2 `release-2` (6), version 3 `release-3` (0). Test (`revie1-test`): version 1 `release-1` (4), version 2 `release-2` (0), version 3 `release-3` (0). **Live (`revie1`) has had nothing pushed and must not until cutover.** A new version only affects new transactions; each transaction keeps the version it started on. Release-3 = release-2 plus the cancellation emails and the coach's fixed-length body. The Dev Test Session listing is on release-3; `BOOKING_PROCESS_ALIAS` decides what newly enabled listings get.
- **Release-4 (Nov 5, 2026):** pushed to Dev (`revie1-dev`) and Test (`revie1-test`) as version 4 with alias `release-4` (0 transactions on each when pushed); the Dev Test Session listing moved from release-3 to release-4 the same day. Live untouched. `render.yaml` now carries `BOOKING_PROCESS_ALIAS=default-booking/release-4`.
- **Release-5 (Nov 12, 2026):** release-4's graph with the corrected cancellation emails. Pushed to Dev only (`revie1-dev`, version 5, alias `release-5`); **not on Test or Live**. The three enabled Dev listings (Test Session, Test Session 1, Test 2) were moved from release-4 to release-5 and their sync signatures re-stamped in the same step (the stored setup already matched, so only `nylasSyncSignature` was written), and the reconcile loop reports them `unchanged`. An enabled listing keeps its own alias in the loop whatever `BOOKING_PROCESS_ALIAS` says (the signature uses the listing's alias), so the loop can never move one back; only new listings take the environment value. `render.yaml` carried `BOOKING_PROCESS_ALIAS=default-booking/release-5` until Nov 16, when it moved to release-6. Existing Dev listings must be switched individually (`scripts/dev-listing-test-helper.js use-release-2`). ## What the inbox count and the topbar dot count
Not unread messages. `fetchCurrentUserNotifications` (`ducks/user.duck.js`) asks Sharetribe for transactions in a list of **state names** that is merged across all registered processes (`getStatesNeedingProviderAttention` / `...CustomerAttention` in `transactions/transaction.js`). The booking process lists none of its own (`statesNeedingProviderAttention = []`, no customer list), so the count comes from a name collision: the unused negotiation process lists `delivered` for customers, which matches a booking's `delivered` state. In practice: **the client's completed sessions that they have not reviewed yet**. A coach's count is always 0. It drops when the client leaves a review. The merge by name is a known template limitation ("subject to problems if one process has a state named similarly"), so removing the negotiation process from `PROCESSES` would silently turn the count off.

## Reading Render's logs, and two traps found on Nov 5
- **Render's request log lines do not contain the path in their text** (`clientIP=… requestID=… responseTimeMS=… userAgent=…`); the method, path and status are in the log entry's *labels*. Searching the text for "/api/nylas/webhooks" finds nothing even when Nylas is delivering. Our own lines are what to search for: `[nylas] webhook POST /api/nylas/webhooks signature=valid trigger=booking.created` (added Nov 5) and `[nylas] booking.created -> accepted`. The Render API (`/v1/logs`, read-only) returns the labels.
- **The sweeper's age cutoff now works (fixed Nov 5).** `lastTransitionedAtEnd` is documented but silently ignored by the Integration API (the same 12 transactions came back for any value, even a made-up parameter), so the sweeper used to grab every paid booking on its next tick. `findPaidUnconfirmedTransactions` now filters on `lastTransitionedAt` in our own code, with a two-minute cutoff on the 60-second tick: the sweeper is a backstop for a closed tab or crashed worker and no longer races the browser's call or the order page's retry. `lastTransitions` is honoured (tested), only the time filter was not.
- **`create-booking` refused every real customer from Oct 27 to Nov 5, and that was invisible.** The caller check (added with the recovery work, PR #6) compared the logged-in user with `tx.relationships.customer`, but a Marketplace API transaction only carries a relationship's reference when it is requested with `include`, so the customer was always "missing" and the browser's fast path always got a 403. Bookings still worked because the sweeper (which had no working age gate) booked them on its next tick, 0 to 60 seconds after payment; the "5 seconds" seen on Nov 4 was a lucky tick, not the US app. Before PR #6 there was no such check and the fast path worked (Sep 13). Now `loadCalendarBookingTransaction` includes `customer`, and `verifyCaller` settles a still-missing relationship from the caller's own orders instead of treating it as "not the customer"; a different user is still refused. The order page also asks once more at ten seconds if the booking is still unconfirmed (safe: a database claim per transaction).

## The 48-hour rule on screen (Nov 26)
A session that starts less than 48 hours from now cannot be moved, and cancelling it is charged in full (the coach cancelling still refunds in full). **One question, asked in one place per side:** the client's screens ask `isInsideFreeWindow(start)` in `src/util/freeCancellationWindow.js`; the server's is `isFreeCancellation()` in `server/api/nylas/scheduler.js` (which decides the refund) with `isInsideFreeWindow()` beside it (which the "You're booked" email uses). `server/api/nylas/freeWindow.test.js` holds the two to the same answers at every offset, the 48-hour boundary included (exactly 48 hours is free). Where it shows:
- **Booking panel:** once a time inside the 48 hours is picked, the line under Book reads "Less than 48 hours away: can't be moved or cancelled for a refund." instead of "Free to cancel up to 48 hours before." (Until a time is picked it says the free line: some days may have both kinds of time.)
- **Checkout summary:** an orange "!" box ("**Less than 48 hours away.** This session can't be moved, and cancelling is charged in full. If {Coach} cancels, you're refunded in full.") replaces the periwinkle "Free to cancel until" box, and the terms line drops "cancel up to 48 hours before for a full refund".
- **"You're booked" and "Session moved" emails:** the free-until sentence is replaced by the same sentence, built as one model value (`freeWindowClosedText`, with the coach's first name) because a Postmark section can only print its own value with `{{.}}`. Templates `booking-confirmed-client` and `session-rescheduled-client` changed (Render Shell: see the HANDOFF of 2026-11-26). `freeWindow.test.js` checks the email's sentence equals the checkout's.
- **The 60-hour reminder is never queued for such a session** (`schedule60hReminder` skips anything under 60 hours, and the sender re-checks `freeUntilOpen` before sending); tested at 30 and 47 hours.
- The booking page's "Your session" card (PR "booking confirmation") has its own copy of the same rule (`rescheduleAllowed`, from the server) and is not changed here.
